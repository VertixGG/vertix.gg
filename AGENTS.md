# Repository Guidelines

## Project Structure & Module Organization
- Monorepo managed by Bun workspaces; all runtime, UI, and tooling code lives under `packages/*`.
- Highlights: `vertix-bot` (Discord runtime), `vertix-base` / `vertix-utils` / `vertix-test-utils` (shared core + mocks), `vertix-gui` and `vertix-flow` (configuration UI), `vertix-website` (marketing site), `vertix-prisma` (database clients).
- Supporting dirs: `docs/` (references), `assets/` (shared imagery), `scripts/` (`ci-jest.bash`, `backup-bot-prisma.js`, etc.).

## Build, Test & Development Commands
- `bun install` – refresh workspace dependencies after cloning or adding packages.
- `bun run vertix:bot:bun:start:dev` – start the Discord bot with Bun hot reload (`vertix:bot:node:start:dev` uses ts-node).
- `bun run vertix:pm2:start` – bring up Redis, the logger, the API, the bot and the pm2 dashboard together (`ecosystem.config.cjs`); pair with `vertix:pm2:logs`, `:status`, `:stop`.
- `bun run vertix:pm2:restart` – ordered cold restart: tears everything down, then starts Redis, logger, API and bot one at a time, waiting for each to accept connections first.
- pm2 never reads `.env`. The dashboard binds loopback on `PM2_DASHBOARD_PORT` (3091) and nginx republishes it to the LAN on 3092; override `PM2_DASHBOARD_HOST` / `PM2_DASHBOARD_PORT` in the shell before `pm2 start`.
- `bun run vertix:flow:dev` / `vertix:website:dev` – boot the flow editor or marketing site; follow with `vertix:website:build` or `:preview` before release.
- `bun run vertix:jest` – run base, bot, and GUI suites in parallel; target a package via scripts like `vertix:bot:jest`.
- `bun run vertix:eslint` or `vertix:eslint:fix` – satisfy linting and auto-fix style issues.

## Coding Style & Naming Conventions
- TypeScript + ESM everywhere; import via workspace aliases like `@vertix.gg/bot/src/...` (guarded by `no-restricted-imports`).
- Default indent is 4 spaces; stylistic rules expect padded braces (`{ value }`), spaced arrays, and no space before function parentheses (`handler()`).
- Name files by feature (`emoji-manager.spec.ts`, `ui-language-definitions.ts`); services/classes stay PascalCase, functions camelCase, env constants UPPER_SNAKE.

## Stored Data Keys
- A data row is filed under `<model name>/<key>` — `ModelDataOwnerBase.normalizeUniqueKeys()` builds it that way — so a model's name is not only a label, it is the key its rows already live under in the database.
- **Spell a stored key as a literal string; never build one from `getName()`.** Deriving it couples the database to a class name, so a rename nobody thought was risky silently repoints every lookup at a key that has no rows: settings read as absent and fall back to defaults, which surfaces as "Could not find master template name in database" rather than as an error anyone can trace.
- Renaming a model therefore takes two changes, not one: the code, and a migration that carries the existing rows over. `scripts/migrate-data-model-keys.ts` does the carrying (dry run by default, `--apply` to write).
- The same goes for any other persisted identifier — a settings key, an IPC action, a cache namespace. They are storage contracts that outlive the code that wrote them.

## Defaults, Stored Sets & Limits
- A stored settings row holds what a generator **was given**; the config `defaults` are what it **is given when nothing says otherwise**. Several call sites mean one while reading like the other, and the difference only shows up on a generator nobody has touched.
- `DynamicChannelElementsGroup.getAll()` is the catalogue — every button that exists. `getDefaults()` is the set a new generator starts with, and each button answers for itself through `isInDefaultSet()`. Pickers, label maps and the `N of M` count want the catalogue; the config default, the wizard's step 2 seed and its fallbacks want the defaults. Resolving a *stored* set back into buttons wants the catalogue too — defaults there would drop a button somebody deliberately enabled.
- **The wizard's seeded set is what gets saved.** `setup-new-wizard-adapter.ts` seeds step 2 and that seed is written on finish, so changing only the config default is invisible: the wizard writes a set containing the button, which then reads as curated and the default never applies to it again.
- **An untouched set is re-read as today's default.** `MasterChannelDataManager.getChannelButtonsTemplate()` maps a stored set matching `V2_DEFAULT_BUTTONS_BEFORE_LFM` onto the current default, so changing that default reaches every generator nobody curated, not only new ones. A set somebody saved carries its own ids and keeps them.
- **A guild settings row is merged over the defaults.** `GuildDataManager.getAllSettings()` answers `{ ...defaults, ...row }`, so a field added to the config after a guild's row was written is still answered from the default. It used to return the stored object whole, which is how a guild that had set one thing read as having set *nothing* for every field added afterwards — worth knowing, because code written against that behaviour was guarding for `undefined` on fields that now always arrive.
- **The dashboard refuses at the same allowance Discord does.** `management-service.getMaxMasterChannels()` asks the bot over IPC, and `management-ipc-service.getConfigLimits( guildId )` answers through `EntitlementService` — per guild, and including whatever tier that guild pays for. It answered one global number for every guild once, which is why a grant used to apply in Discord and not in the dashboard; `constants.masterChannelMaximumFreeChannels` no longer exists.
- **Unlimited crosses that wire as `null`.** The top tier's allowance is `Infinity`, `JSON.stringify( Infinity )` is `null`, so the conversion is made deliberately at the IPC seam rather than discovered on the other side. The reader treats `null` as nothing to hold anybody to, which is what unlimited means there. Anything else printing an allowance goes through `formatMasterChannelAllowance()`, because the one that does not is the one that shows somebody the word `Infinity`.

## Server Branding (Pro)
- **A server can give the bot its own name, avatar, banner and bio - in that server only.** Discord's `Modify Current Member` (`guild.members.editMe`) scopes all four to the one guild, so no server can change how the bot looks anywhere else. It is sold with Pro (`IBillingTier.includesBranding`) and comes with Pro's 14-day free trial, which a server's owner starts once from the dashboard's Subscription page (`POST /subscription/:guildId/trial`, `Guild.trialEndsAt`, `spec/billing-spec.md`) - no room or anything else the bot sees starts one; a hand grant of generators does not include it (`resolveCanBrand()` reads the prices paid and the trial, not the grant). The interface editor stays free.
- **The owner is told two days before the trial ends - in a direct message, once.** `GuildTrialWarningService` claims `Guild.trialWarnedAt` before it sends, so the two shards and the two bots send it once; a server already paying for the plan is skipped (`isTrialWarningDue()`), and a closed inbox loses it - logged, never retried. The end itself needs nothing: the branding sweep takes the profile off and generators past the allowance stop making rooms. The site's pricing page (whose "Start free trial" goes to the Subscription page), terms and refund policy and the dashboard's login, Subscription and branding pages quote the trial from `trialDays`; `site-meta.ts` and the dashboard's no-script `index.html` quote it by hand.
- **Saved profile and applied state are two tables.** `GuildBranding` is what the server asked for (one row per guild, `revision` raised on every save); `GuildBrandingState` is what one bot has put on itself, one row per guild **per application** - because TestVC and production share the database, and each must only undo or count as done what it applied itself. A state older than the bot's own `guild.joinedTimestamp` is read as nothing: a bot removed and added back is a new member with its own face.
- **Every image is re-checked with `parseGuildBrandingImage()` right before `editMe()`.** discord.js resolves an image string that is not a `data:` uri by fetching it as a url or reading it off the disk as a path, and a profile is written by whoever manages a server. The api checks on the way in and the bot checks again on the way out; neither check is optional.
- **Nothing sends an event when a paid period ends**, so `GuildBrandingService` sweeps every `GUILD_BRANDING_RECONCILE_INTERVAL_MS`: a server that stopped paying has its profile taken off (the saved one is kept), one that pays again gets it back. The paddle webhook also publishes `RECONCILE_GUILD_BRANDING` so both happen at once rather than at the next sweep.
- **The name needs Change Nickname, which the invite does not ask for** - the avatar, banner and bio need nothing. Without it the rest is applied and the dashboard says why the name was not.
- Deploying it needs `prisma-migrate-bot-deploy` (a `db push`) on the box for the two new collections.

## Install & Activation Tracking
- **What a server does after adding the bot is written on its `Guild` row**: `joinedAt` / `leftAt` (the latest join and leave - `createdAt` is only the first install ever), `setupAt` (first generator of either kind) and `firstRoomAt` (first room a member made), plus `GuildActivityDay` - rooms made per server per UTC day - and `GuildActivityHour`, the same per UTC hour. `GuildActivationService` records them off `ChannelService.onChannelCreated`, the one place every channel the bot makes passes through. A pool's `SCALING_CHANNEL` rooms are not counted as use: a pool opens them before anybody asks.
- **Join times at startup come from the cache**, because discord.js raises no `guildCreate` for guilds that arrive with `ready`: `CleanupWorker.recordJoinTimes()` copies `guild.joinedAt` onto rows that lack it or hold an older one.
- **Which link an install came from is `GuildInstall`**, written by the api's public `/api/install/callback` only after exchanging the code discord sent back - never from a `guild_id` in the query string, which anyone can type. The sources are the literals in `INSTALL_SOURCES`; each is a storage contract.
- **It is switched off until `INSTALL_CALLBACK_URL` is set**, and that address must also be on the application's OAuth2 redirects in the developer portal or discord refuses the invite. The website and dashboard bake it in at build time. Whether discord redirects a bot-only install at all is not documented - test one install on a throwaway server before relying on it.
- **The bot hands itself out too.** The room panel and the generator panel, V2 and V3, carry `-# ➕ Add VoiceChannels · Vote VoiceChannels` - the invite counted as `bot-room-panel` / `bot-generator-panel`, the vote on discordbotlist (`BOT_VOTE_URL`) because the bot is not public on top.gg yet - under the description, except on the V3 generator panel, whose description closes on "Available Features:", the heading over its button sheet, and the line goes above that. The welcome message's button is `bot-welcome`. `BotInvite` (`apps/vertix-bot/src/utils/bot-invite.ts`) adds the line in each adapter's `getMessage()`, after the build, so it is past the interface editor's reach - and past the language files and the export too, which is why it is English everywhere and missing from the dashboard's preview. A server paying for a plan with branding (`canBrand()`) gets none, and the site's pricing page and the dashboard's billing page say so off the same `includesBranding`. A panel drawn before a purchase keeps it until its next redraw: a room's on its next change, a generator's on the next refresh of its panel. The bot reads `INSTALL_CALLBACK_URL` as it draws.
- **The bot lists carry links of their own** - `listing-topgg`, `listing-discordbotlist`, `listing-discordbots` (discordbots.net), `listing-botlistme`, `listing-boticord`, `listing-discordbotsgg` (discord.bots.gg), `listing-discordlistgg`, `listing-voidbots`, `listing-del` (Discord Extreme List) - pasted into each listing's invite field, so nothing in the code sends them; likewise `post-reddit`, the site's invite page as the r/discordapp post links it (`/invite-vertix?src=post-reddit`). The App Directory's Add App is discord's own install link and is not counted. A new source is only recorded once the api running on the box knows it, so the api goes out before any link that sends one.
- `bun run --env-file=.env scripts/report-activation.ts [--since=YYYY-MM-DD]` prints it, read-only: installs by source, set up in 24h, first room in 7 days, rooms in the last 7 days, still installed, and alive at day 45.
- **The dashboard's Home page reads them.** A server's admin sees its rooms per UTC day (`GuildActivityDay`, 30 days - the days before counting began drawn as not counted rather than quiet), its busiest hours, members and generators ("Server Stats" below), its events' turnout and regulars, and when the bot was added, first set up and first used; everybody sees the rooms made and servers active this week across the network.
- **The owner's figures are a page of their own, `/statistics`**, behind a Statistics link the sidebar shows only when `isOwner`. Every read on it - `GET /dashboard/stats/growth`, `/dashboard/stats/activation`, `/dashboard/stats/usage`, `/dashboard/stats/revenue`, `/dashboard/stats/adoption` - sits in one route scope that `requireOwner` guards (`isOwnerRequest()` against `OWNERD_ID`, never true while it is unset). Growth is what the script prints, worked out by the same `buildActivationReport()`; beside it are the funnel and the time it took to set up, weekly retention cohorts, every install with what it holds now, rooms and active servers across the network, the busiest hours (`GuildActivityHour`, drawn in the viewer's own time zone), the top servers, paying servers and trials, and the features the installed servers use. The arithmetic lives in `packages/vertix-data/src/reports/`, apart from the reads in `statistics-service.ts`. Each part is its own read, so a dashboard ahead of the api says "Failed to load" for what the api does not know yet rather than drawing half an answer.
- Deploying it needs `prisma-migrate-bot-deploy` on the box for the new fields and collections - `GuildActivityHour` among them, counted only from that deploy on - and the api restarted before the dashboard goes out.

## Server Stats
- **Free on every plan, and on the dashboard only.** A server's Home page shows, beside its rooms per day, its busiest hours (its own `GuildActivityHour` rows in the same `HoursGrid` the owner's statistics draw, in the viewer's time zone), its members in rooms this week, the week before and over 30 days, and each generator's rooms over 30 days. Paid stats were considered and dropped: the rooms were already shown free and other bots give the rest away. A weekly summary posted in Discord was built and taken out again on the owner's word - the figures stay on the dashboard.
- **Rooms per generator are `GuildGeneratorActivityDay`**, keyed by the generator's **discord** id - what a room it made holds as `ownerChannelId`, which `ChannelService.onChannelCreated` hands its listeners. Only join-to-create rooms are counted, as for `GuildActivityDay`.
- **Members in rooms are `GuildVoiceMemberDay`** - one row per member per UTC day, counted and never listed, kept `GUILD_VOICE_MEMBERS_KEEP_DAYS` (60) and then deleted by `GuildActivationService.forgetOldMembers()`, which every bot process runs every `GUILD_VOICE_MEMBERS_SWEEP_INTERVAL_MS`. Unlike rooms made, a member in a pool's room counts. **A room's owner is noted when the room is made** (`onChannelCreated` also hands `userOwnerId`), not when they join it: they are moved in before the room's row is written, so their join cannot yet be told for a room's. `GuildActivationService` keeps one note per member per day in memory, so hopping between rooms is one write a day.
- **The privacy policy says it** - which members were in rooms, per day, counted only, deleted after 60 days. Change the keep window and that sentence changes with it.
- Deploying it needs `prisma-migrate-bot-deploy` on the box for the two collections and their unique indexes, then the api, both bot shards, the dashboard and the website.

## Events (check-in, no-shows, attendance)
- **A server's scheduled voice events get a check-in board, no-shows, a "need a sub" post and an attendance log.** Set up from `/setup` -> Events or `/manage events`; free. `GuildEventsService` runs it: a 60 s sweep is the clock (open, freeze, end), voice moves through `ChannelService` `onJoin`/`onLeave` are the attendance. The rules live in `GuildEventRunClock` and `GuildEventAttendance` (`apps/vertix-bot/src/utils/guild-events/`), apart from anything that reads or writes.
- **The clock is the event's scheduled start, not its status.** A voice event is only ACTIVE once a member presses Start, discord completes a started one minutes after its channel empties, and cancels an unstarted one hours after its time. Check-in opens before the start, the roster (the event's "Interested" list, read with `fetchSubscribers()`) freezes after it, and a run ends once its channels have stayed empty or it reaches its longest - each of those is the server's own setting, `GUILD_EVENTS_SETTINGS_DEFAULTS` (15 min, 10 min, 10 min, 12 h) answering until it sets one. `GUILD_EVENTS_TIMINGS` keeps only what no server sets: the sweep, the board's edit spacing and the 24 h cap a run left open across a restart is measured against.
- **Three collections.** `GuildEventSettings` is one row per server, and its `applicationId` is the bot whose setup last saved it - only that bot posts, because TestVC and production share the database. `GuildEventRun` is one occurrence as one bot ran it, unique on application + event + occurrence start (a recurring event keeps its id and moves its start). `GuildEventAttendee` is a member's part in a run; `@@index([guildId, userId])` is there for a later "came to 7 of 9". Phases and error codes are stored literals (`guild-events-definitions.ts`).
- **An event held at a generator or pool counts its rooms**, found through `ownerChannelId` - the generator's **discord** id on a dynamic room, the pool's **row** id on a scaling room. Only confirmed rooms are remembered: a room's row is written after its first member is moved in, and each sweep rebuilds presence from `guild.voiceStates.cache` to catch it.
- **A failure is recorded once and not retried**: `lastError` on the run, and on the settings for the screen to show. A deleted board is never posted again. The bot needs View Channel on the event's channel, and View Channel, Send Messages and Embed Links where it posts.
- Discord needed `GuildScheduledEvents` (not privileged) and the event cache back on (`client-cache.ts`); at size 0 discord.js drops what `GUILD_CREATE` delivers.
- **The dashboard has every setting and the attendance history** (`/events`, free); `/setup` -> Events keeps to a channel and the two switches, names the server's check-in times, and links to the rest (`EventsDashboardButton`). The api (`VertixAPI/Services/GuildEvents`, `/management/guild/:guildId/events/...`) saves only on the bot's word: it asks `get_guild_events_status` over IPC (a wire contract) about every channel and role being picked - the Events channel and the attendance copy's must take a post, a ping role must be mentionable or the bot must hold Mention Everyone - and saves under the `applicationId` of the bot that answered, so a save from the dashboard makes that bot run Events, as `/setup` does. Numbers are accepted only from `GUILD_EVENTS_SETTINGS_CHOICES`. The history cursor is a path segment (`runs/:cursor`, `latest` for the first page) because the dashboard's client sends no query string with a read.
- **Attendee rows carry `displayName`** - the name the server showed, read off the roster (`fetchSubscribers( { withMember: true } )`) or the member's voice state - so the history reads back without asking discord who an id was. Who counts as came, late, no-show or walk-in is one rule, `resolveGuildEventAttendanceKind()`, used by the board and the api alike.
- `discord-options` channels carry `isAnnouncement`: Events posts in plain text channels only, and its picker leaves announcement channels out.
- **A settings row holds only what a server chose.** Every setting past `enabled`, `channelId` and `subPostsEnabled` is null until set, and `resolveGuildEventsSettings()` fills in the defaults - the bot, the api and the dashboard all read a row through it, so none of them can disagree about a setting nobody touched. The bot re-reads it every sweep and keeps it on the run (`IGuildEventRunState.settings`), so a change reaches a run already going within a minute.
- **Pings are the post's content, not its embed.** The board and the sub post are drawn with the adapter's `render()` and sent with `channel.send()`, carrying the mentions and an `allowedMentions` naming exactly those - a role (`checkInRoleId`, `subRoleId`) and, when asked, up to `PING_MEMBERS_MAX` members of the roster not in voice yet. Nothing the adapter's `send()` would have kept is needed: neither post has a component that answers.
- **The least time in voice is kept on the run** (`GuildEventRun.minVoiceSeconds`, written when it ends), so changing `minVoiceMinutes` later never rewrites an attendance already given. Only a finished run is held to it - on the board and in the api alike, through `resolveGuildEventAttendanceKind()`'s `voiceSeconds`/`minVoiceSeconds`.
- `eventChannelIds` limits which events get a run (empty is every one); `logChannelId` gets a copy of each finished attendance, and a copy that fails is recorded on the settings (`log-channel-missing`, `log-channel-forbidden`).
- The dashboard draws the bot's own board, in the server's timing, from `exports/ui/components.json` - its vite config serves that file and copies it into `dist/`, as the website's does. Re-export after changing a board's copy.
- Deploying it needs `prisma-migrate-bot-deploy` on the box for the three collections, `displayName`, the settings' own fields and `minVoiceSeconds`, and the api restarted with the bot - before the dashboard, whose Events page expects the api to know them (it resolves missing ones to defaults, but cannot save them).

## Team Lobby
- **The third kind of master channel: one voice channel people gather in, split into rooms and called back.** Stored as `MASTER_LOBBY_CHANNEL` (the lobby) and `LOBBY_ROOM_CHANNEL` (its rooms), run by `TeamLobbyService` (`VertixBot/Services/TeamLobby`), with who goes where decided by `TeamLobbySplitPlanner`. A split is random teams, pick your team or groups of 2-10 (`TEAM_LOBBY_LIMITS`); Recall moves everybody back and closes the rooms. Made from `/setup` or the dashboard's Generators page (`create_lobby_setup` / `delete_lobby_setup` over IPC, wire contracts); host roles are set in `/setup` only.
- **Free, and it spends a generator slot.** `MASTER_INTERNAL_TYPES` counts lobbies beside generators and pools, as the api's `MASTER_CHANNEL_INTERNAL_TYPES` does, so `/setup` and the dashboard refuse one past the allowance as they refuse a generator. A lobby left past it (oldest setups win, `isMasterChannelCovered()`) refuses Split with `not-covered`; Recall is not held to the allowance - nobody should need a plan to get their members back.
- **Who presses:** the lobby's host roles, the server owner and whoever holds the `/setup` permissions; with no host role named, anybody in the lobby. Bots are never split.
- **Each split opens its rooms in a category of its own, right below the lobby's.** Rooms start from the lobby's permissions, count against `maxActiveDynamicChannels`, and close on Recall or once nobody is left in the lobby or any of its rooms - not as each one empties. At start, `closeAbandonedSplits()` closes the splits everybody walked out of while the bot was away.
- **A team cannot see into another team's room.** Dealt rooms (random teams, groups) are shut - View Channel and Connect - to all but their members and the host roles; picked teams' rooms open to the lobby, or to the members picked, and the first room a member walks into closes the others to them (`keepToPickedRoom()`). The owner, Administrators, host roles and the server's staff roles go anywhere (`getRoamingRoleIds()`). Hence Manage Roles in `TEAM_LOBBY_BOT_PERMISSIONS`.
- **The panel is in two places**: `#🎮・lobby-panel`, a read-only text channel beside the lobby (`lobbyPanelChannelId`; made again on the next draw if deleted by hand, deleted with the lobby), and the lobby's own voice chat. It is a Components V2 container (`setRenderAsContainer( true )`), so a panel posted as embeds is deleted and posted again - an edit cannot turn one into the other. Panels are redrawn at every start as generators' control panels are, skipping one whose drawing hash (`lobbyPanelMessageHash`, `lobbyChatPanelMessageHash`) has not changed; a press always redraws.
- **The server's roles reach a lobby, and a pool, as they are.** Neither has a voice role or a staff list of its own. The server voice role is held in a pool's rooms, in a lobby and in its rooms (`VoiceRoleManager.isVoiceRoleChannel()`), each service calling `syncMember()` on a move through one of its own, after its own work; the server staff roles are let into every room of a split beside the host roles, read as the split opens, so rooms already open keep what they were made with. Staff do not become hosts. Verified roles stay with generators - neither has a private or hidden state.
- **Two messages per member per panel.** A panel press replaces that member's previous screen from it (`shouldDeletePreviousReply( () => true )`), and everything done on a count screen edits that screen - its result and its refusals alike, a deliberate exception to "a refusal posts a notice" below.
- **A count screen is a form.** "👥 Only these members" and the number are only remembered (the screen's args `playerIds` / `count`); ✅ Apply splits. Apply stays off until a number is picked, everyone picked is a person in the lobby, and `getSplitPlanRefusal()` - the check the split itself runs again - finds nothing. The screen is drawn again as picked members come and go, for `TEAM_LOBBY_SCREEN_REDRAW_MS` (14 minutes - Discord stops taking edits to an interaction's reply at 15).
- Deploying it needs `prisma-migrate-bot-deploy` on the box for the two channel types, then the api, both bot shards, the dashboard and the website.

## UI Entity Names
- Everything a UI entity's `getName()` returns — a flow, a state, a transition, an execution step, a button, a modal, an input, an embeds or elements group — is **written out in full at every place it is used**. No local `const` aliasing one, no building one from a shared prefix with a template literal, and no object collecting several of them under short keys for another module to import. An exported `STEPS` map is the same mistake as a `const` alias, one import further away: the use site then reads `STEPS.SENT`, and the name it actually means appears nowhere near it.
- The literal is the only thing tying a use site back to the class that declares it. Spelled out, one search for `"VertixBot/UI-V3/DynamicChannelLimitModal"` finds the class, every adapter that binds it and every page that draws it. Behind an alias or a composed path it is invisible to that search, and an entity nobody can find every user of is one nobody can safely rename.
- Nothing catches a mistake here. These names cross a wire — the bot exports them as JSON and the website and dashboard look them up as strings — so a name that does not match resolves to nothing rather than failing: a guidance entry that never shows, a step whose modal never opens, a transition comparison that is quietly always false.
- `.cursor/rules/always-use-full-names.mdc` states the narrower half of this (flows, transitions, states). It applies to every `getName()` value.
- This does not contradict `never-do-hard-coded-stuff`. That rule is about values that encode behaviour — a limit, a timeout, a word list. An entity name is an identifier, and the full spelling is the point of it.

## UI Copy & Translations
- Any user-facing string in a UI entity (embed title/description/options, button label, select-menu placeholder) is snapshotted into `apps/vertix-bot/assets/languages/*.json` — **the snapshot wins at runtime**, so editing the code alone changes nothing users see.
- Changing such a string is three edits, not one: the code, the seven language files, then re-run the export.
- Export with the enforced command: `bun run vertix:bot:bun:start:dev --export-ui=<repo>/exports/ui`. It exits without connecting the bot. The website and dashboard render from `exports/ui`, so a stale export shows stale copy — and the exporter resolves through the language manager, so a wrong translation gets baked in too.
- Select-menu options are matched by `value` and **fall back to position**, so inserting an option mid-list silently mislabels it — and every option below it. This is how an added button once drew as the name of the one under it, in all seven locales at once.
- Verify with `bun run vertix:languages:check`. It checks that entity *names* exist in every locale, and compares each baked menu's options — how many, and which values — against `exports/ui` and then each locale against en. It still cannot see a stale inner shape or a missing `options` branch, and it lists rather than fails the menus whose baked options carry no `value` at all, since those are the ones position is still deciding.
- **In that list, read which locales it names.** "Matched by position" is a finding, not noise, and which locales appear is the whole diagnosis. Naming the other six but never `en` means those six are missing a `value` the English file has, so the runtime pairs their options by position and inserting one relabels everything below it — in six locales, silently. Naming `en` as well means the bake itself carries no values and there is nothing to compare against. A check merely being cautious would name every locale equally, so an asymmetric list is the bug rather than the caveat. `ConfigExtrasSelectMenu` and `VerifiedRolesEveryoneSelectMenu` sat like that while seventeen of the nineteen menus with options carried values everywhere — an omission, not a convention. Repair it from `en` by **matching the label, not the position**: the labels are template variables and identical across locales, and fixing a positional bug positionally is how it comes back.
- Rewriting a language file programmatically: round-trip it first. `json.dumps( data, ensure_ascii = False, indent = 2 )` reproduces these files byte for byte — **with no trailing newline**, which none of the seven has. Any other indent reformats all seven thousand lines and buries the actual change in the diff, and an added `"\n"` moves the last line of every file for the same reason. Assert the round-trip before writing rather than trusting this line.
- Emoji in translatable content use `EmojiManager.getToken()`, never `getMarkdown()`: an emoji id belongs to the application that exported it, and language files outlive any one application. In an embed, put the emoji in a template var resolved through `setDefaultVars()`.
- **Select-menu placeholders take unicode, not custom emoji.** Discord renders emoji in an embed, a button and a select *option*, but prints a placeholder's markdown verbatim — `<:Name:id> Select User`. The browser preview does render it, so it will look right on the site and wrong in Discord.

## Drawing a UI Screen
- **A success edits the screen; a refusal posts a notice.** That is the whole split, and every adapter that gets it right makes it explicitly: `case "success": await context.editReplyWithStep( interaction, "<step>", { … } )`, and for anything else `return await context.ephemeralWithStep( interaction, "<step>", {} )`. A success redraws a list the owner is already looking at, so it edits; a refusal changed nothing, the screen is still true, and the notice saying why is its own message.
- **It is the editing that keeps a screen to one message, not which function posts it.** Rendering a success through `triggerTransition()` into an `ephemeral` state, or through `ephemeralWithStep`, sends a second copy of the whole screen - and the owner ends up looking at two menus, the older one showing state that has already changed. Swapping one posting function for another does not fix that; only editing does.
- **`UIAdapterBase.ephemeral()` keys its replace-the-previous bookkeeping by `interaction.message.id`** - the message the pressed component sits on, which changes as you move between screens. It is not a per-user slot, and reading it as one leads nowhere.
- **`runInitial( interaction )` dispatches on the pressed button's custom id**, so it only resolves when the *target* adapter owns that button. `VertixBot/UI-V2/DynamicChannelPermissionsAdapter` owns its own access button and can be opened that way; the v3 one cannot, because the button belongs to `VertixBot/UI-V3/DynamicChannelAdapter`, and it throws `Entity ... does not exist in adapter`. Name the step instead.
- **`DynamicChannelAdapterExuBase` and `DynamicChannelAdapterWizardBase` each define `shouldDeletePreviousReply` as a class property.** A property is assigned per instance and shadows the method `ExecutionAdapterBuilder` generates, so the builder's `shouldDeletePreviousReply( handler )` is unreachable for every adapter in those trees and the flag is always true. Removing the property does not restore the hook - the generated method answers false unless a handler is set, and none are.
- **When v2 and v3 differ, read v2's call sites before reading the framework.** The framework is shared and identical for both; the difference is always in how each adapter calls it. One line of `dynamic-channel-permissions-menu-handlers.ts` answered a question that three readings of `ephemeral()` did not, and two framework changes made on the strength of those readings had to be reverted.

## Before Fixing, Prove It Can Happen
- **A failing test is not by itself a bug.** A spec that drives a manager directly can build states the product cannot reach. `DynamicChannelVoteManager` will record a vote for somebody who never registered — but the only button that casts one is generated from the candidate list (`claim-vote-adapter.ts` fills `candidateDisplayNames` from `Object.keys( getResults() )`), so no user can.
- Before fixing, trace the path from the interaction down to the function: grep the method, read the one or two call sites, and check what the UI actually offers. `DynamicChannelVoteManager.$.start()` has a single caller, and the line after it enters the initiator as a candidate — which is what made "the initiator wins with no votes" unreachable, and the guard against it dead code.
- If nothing can produce the state, the fix is speculative edge-handling — `.cursor/rules/avoid-predictive-edge-handle-logic.mdc` — and the test pins fiction. Keep the test if the behaviour is worth stating, but start it where the product starts it.
- Reproductions belong in the existing spec for the thing they test, under the describe that owns the function, not in a new `*-repro.spec.ts` beside it. A second file duplicates the harness, and the name stops being true the moment the bug is fixed.
- Fixture state has to be the state the product leaves behind. The vote unit tests fabricate an event and had omitted its required `timings`, so anything calling `addCandidate` threw instead of asserting — which is why that path had never been covered at all.

## Testing Guidelines
- Jest with `@swc/jest` powers unit/integration tests; specs live under each package's own `test/` and must keep the `*.spec.ts` suffix enforced by each `jest.config.ts`.
- **A spec's path mirrors its subject's path.** `test/` stands where `src/` stands, so the test for `src/ui/general/channel-gone/channel-gone-gate.ts` is `test/ui/general/channel-gone/channel-gone-gate.spec.ts`, and the file is named after the module it covers - a suffix (`ui-adapter-base-cleanup`) only when a second spec covers the same one. A test belongs to the package whose code it exercises, not to whoever happened to write it: a bot spec that only calls `@vertix.gg/base` code is a base spec.
- Things that are not mirrors of a source file go in `test/__test_utils__/` (harnesses, fixtures, casts), and `test/__setup__.ts` stays at the root.
- Resolve paths inside a spec from `process.cwd()`, which jest sets to the package root - never by counting directories up from `import.meta.url`, which goes stale the moment the spec moves.
- Reuse `test/__setup__.ts`, reset ServiceLocator state, and lean on `vertix-test-utils` or `ts-mockito` for doubles.
- New commands, services, or adapters need positive and failure-path coverage before `bun run vertix:jest` (mirrors `scripts/ci-jest.bash`). A package that gains its first spec needs a `jest.config.ts`, a `test/tsconfig.json`, a `<name>:jest` script and a line in both of those runners - otherwise it passes by never running.

## Commit & Pull Request Guidelines
- **Never run `git commit` or `git push` without explicit approval for that specific change.** Show what would be staged and wait for a yes. Approval for one commit is not approval for the next one, and "the work is finished" is not approval to commit it.
- Stage only the files belonging to the change you were asked to make; leave unrelated work in the tree alone rather than sweeping it into the commit.
- Follow the current log style: short imperative subjects with optional scope (`Enhance adapter builders`, `Refactor: streamline embed logic`). Prefix `Refactor:`, `Fix:`, or `Feat:` as needed.
- Squash WIP commits and reference related issues or Discord tickets in the body.
- PRs must state affected packages, schema/env updates, screenshots for GUI/website work, and the commands you ran (`vertix:jest`, `vertix:eslint`).

## Running Instances
- Two bots run against the **same database**: `VoiceChannels` is production on the box (`pm2`, `vertix-bot-0` and `vertix-bot-1`), and `TestVC` is the maintainer's local checkout. Identical data, different code.
- Production is **sharded across two processes**, so a guild is served by exactly one of them - `(guild_id >> 22) % 2` decides which, and `ownsGuild()` is how the code asks. Restarting or reading the logs of one shard therefore says nothing about a guild that lives on the other, which is the likeliest reason a fix looks like it did not deploy. `PM2_BOT_SHARD_COUNT` in `ecosystem.config.cjs` sets the count; `=1` rolls back to a single unsharded `vertix-bot`.
- So a screenshot from `TestVC` proves nothing about what is deployed, and reading the database proves nothing about which code produced the screenshot. Establish which bot a report came from before diagnosing: a local instance can be behind the box by any number of commits while every row you query looks correct.
- When behaviour and stored data disagree, check `git log -1` on the box against the commit that introduced the behaviour, and ask which bot was in the screenshot, before going further into the code.

## Configuration & Security Notes
- The bot loads secrets via `dotenv`; keep `.env*` files local, exclude tokens or Prisma URLs from commits, and prefer `scripts/backup-bot-prisma.js` for encrypted backups.
- **Production builds of the website and dashboard need `.env.production.local`** at the repo root - git-ignored, on the machine that deploys - holding Paddle's live checkout values, while `.env` keeps the sandbox ones for the dev servers. `scripts/base-deploy.js` hands that file to the build as its environment, because bun copies `.env` into every process it starts and vite's `loadEnv()` with an empty prefix lets the environment beat every file - and it refuses to deploy without it, since that build would open the sandbox checkout in production. See `spec/billing-spec.md`.
- Test Discord flows in isolated guilds and avoid posting invite links or member IDs in public trackers.
